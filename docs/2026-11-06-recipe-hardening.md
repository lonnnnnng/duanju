# 接口配方修复与动态扩展评估

- 日期：2026-11-06
- 范围：Android 搜索、详情、取流、配方更新和预取失败恢复
- 状态：本地实现、当前接口抽样及 Redmi Note 8 Pro 真机核心流程已验证；未发布 APK、未推送远程配方

## 1. 选择

保留签名配方分发和内置原生适配器，当前不引入远程 DEX 类加载。配方负责可声明的变化，宿主负责稳定业务模型、签名和解密。出现新协议或新算法时，先用固定向量/响应样本补适配器，再发布 APK。

这不是对所有未来变化的最优保证。目标是降低已经观察到的配置变更成本，同时让失败可以定位、验证和恢复。不能用增加任意执行能力来代替故障分类、请求预算和配置兼容性检查。

## 2. 历史证据与能力边界

核对 `492791d`、`4399396`、`56c215c`、`4e06e81`、`ea817ea`、`4c8bd18`、`87c7733`、`dd583ab` 的差异，并阅读 `0922/hongguo-docs` 下的 `API.md`、`CHAIN.md`、`SIGNATURE.md`、`DUANJU-REFERENCE.md` 与摘要/进度记录。它们是历史实验，不能证明接口今天仍可用。

| 历史变化 | 配方可覆盖部分 | 需要宿主实现的部分 |
| --- | --- | --- |
| 11-06 已有接口补旧签名 | 选择内置 `legacy`、调整顺序 | 签名算法必须已经内置 |
| 10-27 版本改为 74232 | 版本、参数、提取路径 | 返回模型变化超出现有解析器时仍需代码 |
| 10-28 偶发空条目 | 有限重试、退避、指定业务码 | 区分有效空结果与损坏响应 |
| 10-22 HTML 搜索改 JSON API | 新路径与参数 | HTML/JSON 适配、行字段映射、搜索词约束 |
| 10-16 单集模型改批量 POST | 方法、JSON body、提取路径 | 兼容签名请求体的算法与准确分集匹配 |
| 10-21 新 X-Gorgon | 已内置时可按名字选择 | 新算法及固定向量；当前配方仅暴露 none/legacy |

原记录“11 次里仅 1 次需要代码、覆盖约 90%”缺少一致的统计口径，也混入架构迁移和媒体能力变化，撤回该比例。

文档存在时间差：旧 `SUMMARY.md`/`API.md` 部分段落称密钥只能 native 派生；后来的 `DUANJU-REFERENCE.md` 和 duanju 实现已有纯 Kotlin `contentKey` 及向量。应优先核对确切实现和实验日期。`101116` 既有重试恢复记录，也有 `plan/v` 长期业务拒绝记录，不能把它普遍等同临时限流。

## 3. 本轮修复

- 普通 JSON、流式搜索共用请求状态机；空正文先在当前签名档位退避，用完该档预算再换下一档。每次发送重新签名，取消在退避期也能生效。
- 配方控制 `GET`/`POST`、可选 JSON 对象 body、请求头、参数、`extract`、重试条件。JSON 值逐项替换模板，防止关键词引号破坏请求体。带 body 的签名尚未暴露，激活前拒绝不支持的组合。
- 搜索仅把有效结果数组 `[]` 当作无结果；空正文、业务错误、无数组、非 JSON 分别分类。用流式 JSON 读取配方路径，截到结果即结束，不下载调试尾部。
- 首页、详情、取流的解析路径生效；请求和提取使用同一份配方快照。详情精确匹配 seriesId，禁止回退到其它剧首项。行内字段仍由内置适配器解析。
- 损坏签名返回校验失败；逐源处理失败并比较全部可用源，选择有效最高版本。后台与手动检查均保护异常；手动检查禁用重复点击并拒绝销毁视图回调。
- 保存配方时版本检查、原子文件写入和内存激活共用锁；只接受更高版本，写盘失败保留旧文件。错误配方不能凭版本号覆盖现有配置。
- 校验必需端点、schemaVersion、HTTPS 源站、已支持的方法/签名/变量、提取路径和重试预算；每档最多 5 次，退避单项最多 10 秒。
- 去掉详情的额外 3 层重试和预取的整任务立即 3 次重试。预取仅对标为临时故障的异常延迟 20 秒重试，最多追加 3 轮；格式/签名失配持续出现时仍需诊断。

配方 v5 保留原路径/版本/签名顺序，补齐 `empty`、`nonJson`、`missingData`、`http429` 和 `code:101116` 策略。后者是当前四个端点的有限恢复策略，不能套用到所有上游接口。

## 4. 动态类加载、脚本和服务端的取舍

远程 DEX 的实际收益是下发新适配器/算法，不是自动发现新接口。仍要先分析变更、实现并验证，还需处理稳定插件接口、依赖/R8、宿主版本兼容、签名分发、加载失败和回滚；插件异常也会影响宿主进程。

Android 官方建议没有明确业务必要时避免动态代码加载；targetSdk 34 及以上的应用，动态加载的文件还必须在写入前设置只读，否则系统会抛异常。当前项目 targetSdk 为 34，这项约束直接相关。

- [Dynamic Code Loading](https://developer.android.com/privacy-and-security/risks/dynamic-code-loading)，正文访问于 2026-11-06。
- [Android 14：Safer dynamic code loading](https://developer.android.com/about/versions/14/behavior-changes-14#safer-dynamic-code-loading)，正文访问于 2026-11-06。

JS/Lua 等脚本能降低部分解析插件开发成本，但引入解释器、调试和资源限制，并非天然隔离；密码学/native/播放器变化仍有边界。当前不引入。若以后新增解析逻辑反复导致紧急发版，可先考虑受限解析操作或稳定适配器插件接口，再用明确故障样本评估脚本或 DEX。

服务端解析可以集中修复，但会重新引入服务端依赖和可用性成本，与既有手机纯直连目标冲突。当前不把它作为默认方案。

后续值得做的是经过当前网络实测的多 provider 适配、发布前样本验证和运行期健康探测。不能把历史失效接口直接塞进兜底列表，也不能自动回滚到已经不适应上游的旧配方；运行期按健康状态切换需要独立设计和验收。
