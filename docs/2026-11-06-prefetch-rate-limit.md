# 自动预取下一集失败修复报告

- 日期：2026-11-06
- 版本：v0.1.37（未发布，代码已合入 main）
- 影响范围：安卓播放页「预加载下一集」、切集命中率
- 状态：已修复，真机验证通过

> 本文保留当时的实验记录，不代表本轮修复已做设备验收。后续审查发现请求层的空响应重试未生效，
> 并且这些日志不足以唯一确定“限流”根因。当前已移除整任务立即重试，改为统一请求预算与有限延迟恢复；
> 见 [配方修复与动态扩展评估](2026-11-06-recipe-hardening.md)。

---

## 1. 现象

用户反馈：**自动预取下一集很容易失败，但过一会儿手动点同一集又能正常下载播放。**

界面表现：

```text
第1集 · 1080p · 26.1 MB · 126s / 143s
第2集预取失败
```

手动点第 2 集后，下载与播放正常。

## 2. 复现与日志证据

清空数据 → 首页 → 详情 → 播放第 1 集，观察日志：

```text
18:40:30.963  PlayerActivity: 第1集解析1666ms 下载2448ms
18:40:31.213  PlayerActivity: 预取第2集失败(1/3)：空响应(HTTP 200)
```

关键点：**本集下载完成仅 250ms 后就请求下一集**，第一次预取立即拿到 `HTTP 200 + 0 字节`。

对照 Mac 直连同一接口（有效签名）：

```text
ep idx=1 try1 -> 200 23239B
ep idx=1 try2 -> 200 23239B
ep idx=2 try1 -> 200 22076B
ep idx=2 try2 -> 200 0B      ← 同一分集连续请求时偶发
ep idx=1000 try1 -> 200 22695B
ep idx=1000 try2 -> 200 22712B
```

说明：**有效签名下取流接口本身会间歇返回 0 字节**，与签名无关，属上游限流/网关抖动。

## 3. 根因

1. 播放流程是「请求详情 → 请求取流 → 下载解密本集」，紧接着预取又「请求详情 → 请求取流 → 下载解密下一集」，
   短时间内对同一域名产生连续取流请求。
2. 上游对这些连续请求限流，返回 `200 + 0 字节`（网关层，不是业务码）。
3. 旧实现：预取只尝试一次，失败即放弃，且异常被静默吞掉（无日志），用户只看到「预取失败」。
4. 用户手动点下一集时，距上次请求已过去数十秒，限流窗口已过，因此成功。

这与「上游在签名/免签之间振荡」不同：**0 字节不一定代表签名错误，也可能是高频限流。**

## 4. 修复

`PlayerActivity.kt`：

1. **复用分集列表**：播放本集时已拿到 `chapters`，预取直接复用，
   不再重复请求一次详情（少一次被限流的机会）。
2. **整任务重试 3 次**：任一步失败（0 字节 / 网络 / 解密）都整段重来，
   失败原因写日志（`预取第N集失败(i/3)：原因`）。
3. **后台延迟重试**：3 次仍失败时，若用户仍停留在本集，每 20 秒再试，最多 3 轮；
   切集 / 退出 / 页面销毁时通过 `prefetchRetryRunnable` 自动清理。
4. 播放失败也记录集数、错误与 vid，便于和上游响应对照。

配方侧（`assets/recipes/hongguo.json` v4）：

- `media` 重试 4 次、退避 1/2/3 秒（此前 3 次、0.6/1.2 秒），用于吸收单次请求的间歇 0 字节。

## 5. 验证

### 5.1 断网强制失败 → 恢复（验证延迟重试）

播放第 1 集后关闭 Wi-Fi，50 秒后恢复：

```text
18:51:52  预取第2集失败(1/3)：解密失败: rc=1
18:52:01  预取第2集失败(2/3)：Unable to resolve host ...
18:52:13  预取第2集失败(3/3)：Unable to resolve host ...
18:52:13  预取第2集将在20s后重试(1/3)
18:52:33  预取重试触发：foreground=true selected=1 target=1
18:52:40  预取第2集失败(1/3)：Unable to resolve host ...
18:52:49  预取第2集完成
```

### 5.2 正常网络（验证命中与连续预取）

```text
第1集解析582ms 下载2196ms
预取第2集完成
→ 点第2集：第2集命中缓存 9502976B
→ 预取第3集完成
```

换剧复测同样正常（`vid=... 分集数=129`，首集解析/下载/预取均成功）。

## 6. 说明与遗留

- 测试期间一部 1000 集的剧在真机上持续失败，而 Mac 同参数正常：
  判断为高频测试触发的 IP/设备限流，不是代码问题；冷却后复测正常。
- 首集播放本身没有「整任务重试」，只有配方内 4 次重试；
  若上游长时间限流，用户重新点击播放即可（状态行会显示具体原因）。
- 判定口径更新：`200 + 0 字节` = 网关拒绝（签名/档位不对 **或** 高频限流），
  已有退避重试兜底。
